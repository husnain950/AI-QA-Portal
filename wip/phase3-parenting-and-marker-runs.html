Fix one The message said "out of order". It was in the wrong chapter.

A definition clause is not a section

Section 33A binds its real body — 2[33A. Proceedings against authority and persons.– at page 75, 911 characters — but sat under CHAPTER I PRELIMINARY, which otherwise holds sections 1 and 2 at page 2. Tracing discovery on that TOC-less edition: 

discover: 0 chapters, 126 sections
  parent=None <- ['1', '2', '3', '3B', '4', '5', '6', '7', '7A', '8']

Every section comes back parentless, so insert_missing_body_chapters builds the whole tree — assigning sections by which codes are printed in each chapter's span. And the Act defines "supply chain" as clause [(33A) inside section 2, which puts 33A in CHAPTER I's span. CHAPTER I is processed first and claims it; CHAPTER VII, 55 pages later, finds the parent already set and skips it.

An entry carrying an anchor knows where it is. It is now placed by position, never by code membership.

The lock passed with the fix removed

The first fixture had two chapters and passed either way — with only two, the second pass reassigns 33A anyway, because its parent is the previous chapter and the entry.parent is prev clause allows it. The real document has ten chapters in between.

Adding a CHAPTER II reproduces the defect, and the lock now fails when the anchor branch is stubbed out. A lock that cannot fail is worth less than no lock, because it gets believed.

Fix two Round 4 was right to refuse the wide version.

Two markers, one space

Customs s.202B was a heading-only stub in four editions, its body left inside s.202A. Round 4 measured the naive MARKER_PREFIX widening at 1 fix : 17 false positives and declined it. The narrow form admits the branch only behind a lookahead for [CODE. Capital — which over 186,971 lines matches exactly one.

202B46 → 1,256 chars
33ACHAPTER I → CHAPTER VII

The first attempt matched the rendered output and missed the document

why_unbuilt.py said 202B … code never opens a body line while _candidate_code returned 202B on the line I had tested. They were not the same line: 

parser's line text   '42 53 [202B. Reward to officers ...'   ← space before the bracket
rendered plain_text  '42 53[202B. Reward to officers ...'    ← the rendering collapses it
Every gained/lost measurement in this phase has used output/*.json plain_text as its corpus. That is a good approximation and it is not what the parser sees.

The corrected pattern allows whitespace on both sides of the run's tail, still matches only that one line, and the lock pins both spellings.

Fix three Found while reading the task list, not the code.

A stale report hid a broken generator

wip/tasks.md asks to re-examine "the 29 low-confidence documents in report.md §5". That section listed two.

Its filter tests BY_LABEL[family].profile. Phase 2 made a family's profile an override — only amending names one, and consolidated is None because the lane's own profile is right for it. So since PR #45 the predicate has been truthy for amending alone, dropping 27 of the 29 rows. 

consolidated   profile=None       parseable=True
amending       profile=<Profile>  parseable=True

Nobody saw it because report.md had not been regenerated since Phase 0 — it kept printing the old 29 while its generator produced 2. Round 6's --write surfaced the break, which means PR #51 shipped a report with 27 rows missing. The data in signatures.json was always complete; only the view was wrong.

One word: .profile → .parseable, the field Phase 2 added for exactly this question. §5 is back to 29 rows and signatures.json is untouched.

Third instance of one pattern this phase, after the stale in-code skip in round 2 and the two stale exemptions in round 3: a cached artifact cannot tell you its generator is wrong.
