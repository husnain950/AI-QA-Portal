Why this matters more than it looks. Before, this dict and its parent chapter were the same shape. A consumer told a container from a leaf by guessing which keys happened to be present — sections for one, html for the other. toc.Node.kind had always computed the answer, and _node_to_dict had always thrown it away.

That last row is a node the old model could not describe: a schedule part that carries html and plain_text directly instead of children. Positionally a part, functionally a leaf — and now it says "type": "part" rather than leaving the reader to work it out.

03 An amending act: one chapter deleted

The Tax Laws (Amendment) Act, 2024 declares no chapters. It printed one thing that looked like a container, and the parser believed it.

The Tax Laws (Amendment) Act, 2024chapters[0]
{ "code": "PART I", "heading": "Acts, Ordinances, President’s Orders and Regulations NATIONAL ASSEMBLY SECRETARIAT", "toc_heading": "Acts, Ordinances, President’s Orders and Regulations NATIONAL ASSEMBLY SECRETARIAT", "heading_source": "toc", "sections": [ /* all four real clauses of the Act */ ] } { "code": "", "type": "chapter", "node_key": "ch:~root", "sections": [ /* the same four clauses, unchanged */ ] }

“PART I — Acts, Ordinances, President’s Orders and Regulations / NATIONAL ASSEMBLY SECRETARIAT” is the masthead of the Gazette of Pakistan. It is the name of the publication section the Act was printed in. It was being served as a chapter of the Act, with the Act's four clauses filed underneath it.

The replacement carries code: "" — the synthetic root a flat act already got, now named ch:~root rather than given a position. The four clauses, their codes, headings, page ranges, HTML and footnotes are identical on both sides. Only the false parent is gone.

05 node_key: identity by code, not by position

existing · source_key
"/chapters/0/sections/3" array position. Minted into a UUID5 by json_parser._stable_id. Insert a node above this leaf and every id below it is re-minted — which orphans the reviewer annotations attached to them.
new · node_key
"ch:vii/pt:i/s:114" the ancestor chain by the codes the statute itself prints. Sits BESIDE source_key and changes no existing id, so this needs no migration — it is a handle for the diff work, put in place before it is needed.

This does not solve versioning, and was not meant to. It makes sure the identity scheme built next has something to hold on to other than an array index.

06 Scope, honestly

Three limits a reviewer should know before reading the on-disk corpus.

fbr_ingest diverges by 3,500+ lines and its merge is an explicit v1 non-goal (README.md:283). This PR does not relitigate that — it supplies the numbers to decide it with. The consequence for now is real: the 12 converted Income Tax Ordinance editions keep the old node shape, so type and node_key are not yet universal across the corpus.

The on-disk JSON has not been regenerated. Every excerpt on this page comes from a conversion run for this review. Re-converting all three lanes is Phase 2 in wip/tasks.md, and it is blocked on OCR — the virtualenv is Python 3.14.7 against a 3.12 pin with numpy absent, which also stops two amending instruments converting at all.
