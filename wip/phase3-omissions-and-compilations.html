The glyph 279 occurrences, 5 editions — 250 of them in one.

Is (cid:2) recoverable? No, and the font says why

_is_omission exists so a heading-only leaf is not reported as missing its body when the law itself omitted the section. It matches omitted / repealed / ***. Eight leaves print their omission like this: 

Omitte(cid:2)d
hav(cid:2) b(cid:2)(cid:2)n (cid:2)xport(cid:2)d   → "have been exported"

(cid:N) is what pdfplumber emits for a glyph whose font subset carries no ToUnicode entry. Before tolerating it, the question worth asking is whether it can be recovered. Measured on The Sales Tax Act, 1990 (01.07.2014), which holds 250 of the 279 occurrences, the answer is no — and the reason is specific:

HAAAAA+
<02>→r
JAAAAA+
<02>→8
ABAAAA+
<02>→4
DBAAAA+
<02>→l
BAAAAA+
no <02> entry

The producer emitted dozens of separate LinuxLibertineG subsets, each with its own small CMap. Glyph <02> means a different character in every one — and the subsets that actually print (cid:2) are exactly those missing that entry. BAAAAA+ lists 83 mappings and skips it.

There is no consistent mapping to recover, and none was ever written down. The character is unreadable.

So the invariant drops it before matching, which is what lets Omitte(cid:2)d read as the omission it is. 111 → 103.

The compilations 48 hits — two documents that are not one instrument each.

A leaf built from an index row has no body to carry

Customs Rules, 2001 — 44 hits. 563 pages binding 44 separately notified S.R.O. rule sets behind a single index. The tree has no level above chapter, so the index rows become the section leaves: 

Passenger's Baggage (Import)Rules. 570(I)/98 dt.12.06.1998
Frustrated Cargo Export Rules 3(I)/70, dt 2.1.1970  86-89

Federal Excise Rules 2005 — 4 hits. PDF page 75 starts a second instrument inside the body — Electronic Filing of Federal Excise Return Rules, 2005, with its own contents page — whose rows are parsed as this document's rules 1–4, carrying leader dots where their text should be.

None of this is new evidence. Both documents already carried exemptions on sibling invariants for exactly this cause, and Customs Rules 2001 also carries a known_gap case. The invariant is right; the pipeline cannot express the document. The fix is the instrument tree level, now written down as Phase 5 — and the test that it worked is the deletion of these entries.

An exemption does not hide a failure's size: the invariant still runs and the report still prints [44 hit(s)] beside the reason.

The suite handed back two dead entries

Adding entries made the runner re-check the existing ones, and it reported two as no longer failing: 

Customs Rules, 2001        [no longer failing] no_orphan_marker_li
Federal Excise Rules 2005  [no longer failing] section_codes_ordered
            exemption is now stale -- delete the entry

Both had been fixed by earlier rounds and nobody noticed. Deleted, as the report instructs.

This is round 2's lesson arriving from the opposite direction. There, a skip hardcoded inside a check function had gone stale in silence, because nothing re-examines a condition buried in code. Here the declared format did the work unasked — it surfaced dead entries as a side effect of an unrelated change. The rules lane ends the round with 8 exemptions: two added, two removed.
